# The Browser page

`More -> Browser` in the app. Two panes:

- **Live** (the default): every window of the browser, live, and the owner's hand in any of them,
  and the window the VNC screen shows -- `docs/browser-live.md`.
- **VNC**: how a human takes the browser over from outside the app right now, without asking the
  agent and without an account on the host. The rest of this page is about that pane.

## Why the password is shown

The page displays the VNC password in clear, on request. That is deliberate, and it is not a
weakening: a paired device already runs the agent, and the agent has a shell. Anyone who can open
this page can already read `~/.vnc/passwd` by typing one sentence. Hiding it here would protect
nothing and would only push the owner towards a second machine to look it up, which is what the
page exists to avoid.

The trust boundary is the pairing, not this page. If that ever stops being true -- if the channel
grows a reader role that cannot run tools -- this frame has to grow a check with it.

## Where the password comes from

`~/.vnc/passwd`, read back and decoded (`src/browser/vnc.ts`), overridable with
`browser.vncPasswordFile`.

`vncpasswd` does not hash: it DES-encrypts the password under a key that is a constant of the
protocol, so the file is recoverable by design and every VNC client on earth does this. Two
consequences the page inherits:

- **The file stays the only copy.** Putting the password in `config.json` would place a secret in
  a hot-reloaded file and leave two versions to drift the first time it is rotated.
- **Only the first 8 characters exist.** The format stores one DES block. A longer password is
  silently truncated, which the page must not pretend otherwise.

`tests/browser/vnc.test.ts` pins the decoding against blobs produced by the real
`x11vnc -storepasswd`. A fixture generated by the module under test would agree with any key,
including a wrong one.

## What the frames carry

`browser.info` -> `browser.info.result`:

| field | source |
|---|---|
| `webUrl` | `browser.novncUrl` |
| `vncHost` | the hostname of that same URL |
| `vncPort` | 5900 |
| `password` | the decoded file, absent when there is none |
| `services` | `systemctl --user is-active` over `browser.units` (the installer's units are user units; before 0.7.82 the system manager was asked and every unit read down) |
| `tabs` / `tabsError` | the browser's own list of tabs (no page is asked anything); the app shows the live listing instead |

`vncHost` is derived from `webUrl` rather than configured separately, so the web client and the
native client can never be told to dial different machines.

## Failures are in-band

A sidecar that is down is exactly when someone opens this page. So a failure to list tabs is
reported in `tabsError` and the frame is still sent: refusing it would also withhold the service
list, which is the part that explains why the browser is unreachable. Only a failure to build the
answer at all is refused.

A unit that does not exist, or a host without systemd, reports as down rather than throwing.

## Unlock

`browser.unblock` -> `browser.unblock.result` (`src/browser/unblock.ts`,
`handleBrowserUnblock`), and the page's button is the whole UI for it.

**The failure it answers, measured 2026-09-21.** Chromium opens a GTK "Open File" chooser for a
page's `<input type=file>`. The display this install runs (`Xvfb :99`) has **no window manager**,
so nothing raises a dialog above its parent or hands it the input focus: the chooser sat behind
the browser window -- only its 20px edge showed, along the top-left -- while its modal grab ate
every click. The browser looked perfectly normal and nothing was clickable, anywhere.

**The rules are the design**, and they are pure functions in `src/browser/unblock.ts`:

| window | decision |
|---|---|
| a name ending in `chromium` (a page window, a helper), or no name at all (the root) | never touched |
| a title that names an action (`Open File`, `Save File`, `Select Folder`, `Ouvrir…`) | raised, focused, closed with `Escape` |
| anything else visible | raised and focused, **never** closed -- only the owner knows whether it was wanted |

The order is not cosmetic: `xdotool key` goes to whoever holds the focus, so a dialog is focused
*before* the Escape is sent. The page window is raised and focused last, because closing a dialog
this way leaves no window focused at all and the next click would type into nothing.

`xdotool` is the one host dependency (`apt-get install xdotool`); a host without it gets that
sentence in the result rather than a refusal, because it is the one failure here with an obvious
fix. The display is `browser.display`, `:99` by default -- the one `my-claw-chromium.service`
runs on.

This unblocks; it does not guard. A file chooser that opens while nobody is looking for one is
closed only when the button is pressed.
